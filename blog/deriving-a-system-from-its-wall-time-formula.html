Deriving a system from its wall-time formula

At Effective, we build and host insurance rating algorithms. A rater maps a risk to a premium or an explicit rejection. Calling one is an ordinary API request; calling it over a carefully chosen input space reveals how a carrier prices a market.

In Designing a compiler for an agent-written DSL, I wrote about giving agents fast, structured feedback while they build raters. Once a rater runs, the next loop is simple: generate inputs, evaluate the program, inspect the results, and decide what to try next.

analysis cycles per session ≈ session duration / (model latency + system latency)

We use frontier models through an API, so model latency is mostly outside our control. That leaves the systems they call. Here, I am looking at the time it takes to run a rating algorithm over enough inputs to answer a useful question.

For the measurements below, we treat the deliberately naive execution path—calling the single-input API 100,000 times sequentially—as the 1× baseline.

What properties do we want?

  • Bounded memory. We hold at most one bounded page or partition in any API process, workflow, or worker.
  • Durable progress. We derive partition, invocation, and output identities from the run, so retries converge without recomputing committed results.
  • Explicit concurrency. Physical workers determine how many rater processes can exist.
  • A small control plane. Workflows carry references and completion state; object storage carries inputs and outputs.

The simplest way to get those properties is to keep each unit of work small. We split a batch into immutable partitions with a configured row limit and give each executor one partition. Each rater gets one task per partition.

We choose a partition size that fits in memory, make work at that size predictable, and reject anything larger before it causes an OOM kill. This keeps the system easy to reason about (see: Static Allocation, Constant Work).

Why Temporal?
  • Workflows are the durable control plane. A batch workflow receives a manifest reference, derives its tasks, records completed artifact references, and commits the ordered output. Replay recovers that coordination after a process disappears.
  • Activities are the bounded execution and retry units. One activity owns one (partition, rater) pair and its deterministic artifact, so computation, persistence, timeouts, and retries share a boundary.
  • Task queues separate work from capacity. The workflow exposes partition work, fixed-capacity workers pull only what they can run, and queue depth drives autoscaling.

Each rating has an evaluation cost. Each partition also pays a fixed cost for loading the rater, crossing a process boundary, validation, and commit. If we average those costs across the workload and count only the workers that stay busy, we get:

wall time ≈ total ratings / effective workers × (evaluation time + fixed cost / partition size)

The formula points to a few obvious knobs. The next sections amortize fixed cost, keep per-rating data off the control path, align retries with partitions, and add effective workers.

1. Amortize fixed overhead inside a bounded unit

Calling the single-input API pays the fixed cost for every row. A partition pays it once:

single-row calls ≈ inputs × (evaluation time + fixed cost) partitioned calls ≈ inputs × (evaluation time + fixed cost / partition size)

We send each ordered partition through an already loaded rater process.

Outcomes retain their input positions, including mapping and rating failures. We persist each partition’s deterministic execution records in one atomic operation, turning one database round trip per input into one per partition.

Bulk execution and atomic persistence bring the cumulative speedup to 6×.

2. Keep batch data out of executor memory

A file ID only helps if we leave the file where it is. Downloading the complete artifact before starting the workflow merely moves the memory limit into the API process.

Our run API accepts an immutable input manifest. Each activity receives a partition reference and reads only its partition. A completed (partition, rater) task writes one immutable rated artifact; the final manifest orders those artifacts and commits the run.

We index individual executions for search and UI history after committing the output manifest. This cheats a little on completion semantics: the result becomes durable before every execution becomes searchable. The manifest remains the source of truth, and a durable workflow owns the remaining indexing work. This removes work proportional to the number of ratings from the next agent turn’s critical path.

artifact storage = O(total ratings) control-plane state = O(tasks)

Streaming input preparation and eventual execution indexing bring the cumulative speedup to 10×.

3. Make computation, persistence, and retry the same unit

We make (partition, rater) the unit of computation, persistence, and retry. It maps one partition, evaluates it with one loaded rater, and writes one rated artifact.

The short-lived mapper exits before we load the rater, isolating arbitrary mapping code without putting two large processes in memory together. A deterministic artifact ID lets retries reuse results committed before an acknowledgement was lost. A failure can recompute at most one partition.

We gather artifact references in input and rater order, so no worker reconstructs the full output. Partition-native execution brings the cumulative speedup to 16×.

4. Scale by adding fixed-capacity workers

Each worker admits one activity and loads one rater process. Additional work waits durably in Temporal instead of consuming process memory.

Workflows bound outstanding tasks; Kubernetes bounds executing workers. Partition-queue depth drives autoscaling.

executor memory = O(partition size) fleet memory = O(partition size × workers)

Eager partition dispatch and activity-aware scaling bring the cumulative speedup to 17×.

Where is the headroom?

The wall-time formula also shows how each knob affects wall time:

wall time ≈ total ratings / effective workers × (evaluation time + fixed cost / partition size) 1% ↑ effective workers → ≈ 1% ↓ wall time 1% ↓ evaluation time → scaled by evaluation’s share of wall time 1% ↓ fixed cost → scaled by fixed cost’s share of wall time returns from larger partitions decay quadratically

Once the partition is large enough to amortize loading the rater, this suggests the following tuning sequence:

  1. Improve utilization, then add workers. Wall time scales inversely with both only while enough work keeps the added workers busy.
  2. Reduce evaluation time. A native RSL evaluator, better table indexes, and faster common expression paths reduce work paid for every input.
  3. Reduce fixed cost. Warm runtimes, parsed tables, cheaper serialization, and cheaper artifact commits reduce the cost amortized across each partition.
  4. Increase partition size. Returns decay while memory grows linearly, so we stop when a partition approaches the worker’s memory limit or fixed cost is already small next to evaluation time.

Evaluation time, fixed task time, memory per row, and utilization tell us whether this sequence applies before we implement each change.

What does this let us learn?

RSL declares the valid input domain, so we can sample a deployed pricing algorithm deliberately. We can vary inputs across one pricing surface to find discontinuities, interactions, and non-monotonic behavior, or run the same risks across carriers to compare appetite, premiums, and changes in ranking.

At baseline, an experiment with 100,000 ratings is a background job. At 17× the throughput, it fits inside an interactive loop. A human may struggle to interpret results any faster, but an agent can aggregate them, choose the next interesting region, and continue. If rating remains the bottleneck and each experiment is similarly useful:

hypotheses tested per session ∝ rating throughput

Deriving a system from its wall-time formula

At Effective, we build and host insurance rating algorithms. A rater maps a risk to a premium or an explicit rejection. Calling one is an ordinary API request; calling it over a carefully chosen input space reveals how a carrier prices a market.

In Designing a compiler for an agent-written DSL, I wrote about giving agents fast, structured feedback while they build raters. Once a rater runs, the next loop is empirical: generate inputs, evaluate the program, inspect the results, and decide what to try next.

analysis cycles per session ≈ session duration / (tₘ + tₛ)

Each cycle waits on the model (tₘ) and the systems it calls (tₛ). We use frontier models through an API, so tₘ is mostly outside our control. This post reduces a large component of tₛ: running a rating algorithm over enough inputs to answer a useful question.

Our deployed raters are currently generated Python programs. The design only assumes that loading a rater costs enough to amortize over many inputs, so it also applies to a future native RSL runtime.

A batch of N inputs over R raters produces NR ratings. We use 100,000 ratings as the representative workload below.

For the measurements below, we treat the deliberately naive execution path—calling the single-input API 100,000 times sequentially—as the 1× baseline.

What properties do we want?

  • Bounded memory. We hold at most one bounded page or partition in any API process, workflow, or worker.
  • Durable progress. We derive partition, invocation, and output identities from the run, so retries converge without recomputing committed results.
  • Ordered results. Parallel execution preserves the order of a sequential map over inputs and raters.
  • Explicit concurrency. Physical workers determine how many rater processes can exist.
  • A small control plane. Workflows carry references and completion state; object storage carries inputs and outputs.

Those properties give us a natural unit of work. To keep process memory fixed as a batch grows, we split it into immutable partitions bounded by a row limit (P) and give each executor one partition.

partitions = ⌈N / P⌉ tasks = R⌈N / P⌉
total work = Θ(NR) work per task = O(P) = O(1), for fixed P

We pick P, make work at that limit predictable, and reject excess before the machine discovers the limit through an OOM kill, following Static Allocation, Constant Work.

Why Temporal?
  • Workflows are the durable control plane. A batch workflow receives a manifest reference, derives its tasks, records completed artifact references, and commits the ordered output. Replay recovers that coordination after a process disappears.
  • Activities are the bounded execution and retry units. One activity owns one (partition, rater) pair and its deterministic artifact, so computation, persistence, timeouts, and retries share a boundary.
  • Task queues separate work from capacity. The workflow exposes partition work, fixed-capacity workers pull only what they can run, and queue depth drives autoscaling.

Each rater (r) has a per-input evaluation time (eᵣ) and a fixed task cost (Fᵣ). Across W workers, scheduling and uneven task durations reduce utilization (U ∈ (0, 1]), giving us this wall-time model:

wall time ≈ N / UW · Σᵣ(eᵣ + Fᵣ/P)

The formula gives us the performance levers. The next sections amortize Fᵣ, keep O(NR) data off the control path, align retries with partitions, and increase UW.

1. Amortize fixed overhead inside a bounded unit

Calling the single-input API pays Fᵣ for every row. A partition pays it once:

one row per task ≈ N(Fᵣ + eᵣ) P rows per task ≈ N(eᵣ + Fᵣ/P)

We send each ordered partition through an already loaded rater process.

Outcomes retain their input positions, including mapping and rating failures. We persist the partition’s deterministic execution records in one atomic operation.

database round trips: N → ⌈N / P⌉

Bulk execution and atomic persistence bring the cumulative speedup to 6×.

2. Keep O(N) data outside O(1)-memory executors

A file ID only helps if we leave the file where it is. Downloading the complete artifact before starting the workflow merely moves the memory limit into the API process.

Our run API accepts an immutable input manifest. Each activity receives a partition reference and reads only its partition. A completed (partition, rater) task writes one immutable rated artifact; the final manifest orders those artifacts and commits the run.

We index individual executions for search and UI history after committing the output manifest. This cheats a little on completion semantics: the result becomes durable before every execution becomes searchable. The manifest remains the source of truth, and a durable workflow owns the remaining indexing work. This removes an O(NR) projection from the next agent turn’s critical path.

artifact storage = O(NR) control-plane state = O(R⌈N / P⌉)

Streaming input preparation and eventual execution indexing bring the cumulative speedup to 10×.

3. Make computation, persistence, and retry the same unit

We make (partition, rater) the unit of computation, persistence, and retry. It maps one partition, evaluates it with one loaded rater, and writes one rated artifact.

The short-lived mapper exits before we load the rater, isolating arbitrary mapping code without putting two large processes in memory together. A deterministic artifact ID lets retries reuse results committed before an acknowledgement was lost.

maximum recomputation after failure ≤ P ratings

We gather artifact references in input and rater order, so no worker reconstructs the full output. Partition-native execution brings the cumulative speedup to 16×.

4. Scale by adding fixed-capacity workers

Each worker admits one activity and loads one rater process. Additional work waits durably in Temporal instead of consuming process memory.

Workflows bound outstanding tasks; Kubernetes bounds executing workers. Partition-queue depth drives autoscaling.

executor memory = O(P) fleet memory = O(PW)

Eager partition dispatch and activity-aware scaling bring the cumulative speedup to 17×.

Where is the headroom?

The wall-time formula also ranks the next optimizations:

wall time ≈ N / UW · Σᵣ(eᵣ + Fᵣ/P) 1% ↑ W or U → ≈ 1% ↓ wall time 1% ↓ eᵣ → [eᵣ / Σᵣ(eᵣ + Fᵣ/P)] × 1% ↓ wall time 1% ↓ Fᵣ → [(Fᵣ/P) / Σᵣ(eᵣ + Fᵣ/P)] × 1% ↓ wall time ∂ wall time / ∂P ∝ -1/P²

For the common case in which evaluating a rater costs more than starting it, this suggests the following ranking:

  1. Improve the mechanisms behind U, then increase W. Wall time scales inversely with both only while enough work keeps the added workers busy.
  2. Reduce eᵣ. A native RSL evaluator, better table indexes, and faster common expression paths reduce work paid for every input.
  3. Reduce Fᵣ. Warm runtimes, parsed tables, cheaper serialization, and cheaper artifact commits reduce the amortized term Fᵣ/P.
  4. Increase P. Returns decay as 1/P² while memory grows as O(P), so we stop near the worker’s memory limit or when Fᵣ/P ≪ eᵣ.

Evaluation time, fixed task time, memory per row, and utilization tell us whether this ranking applies before we implement each change.

What does this let us learn?

A fast batch rater lets us probe a deployed pricing algorithm. Because RSL declares the valid input domain, we can generate valid risks and targeted inputs near type, table, and eligibility boundaries.

25,000 base risks with four controlled variations produce 100,000 points on one pricing surface. We can measure marginal premium effects, find discontinuities, check monotonicity, and locate interactions between inputs.

10,000 risks across ten carriers produce 100,000 premiums. We can compare appetite, find the cheapest carrier by segment, and locate small changes that reverse carrier rankings.

At baseline, each question becomes a background job and encourages us to choose a few representative examples. At 17× the throughput, the same workload fits inside an interactive loop.

For a human, 100,000 premiums can arrive faster than they can decide what the results mean. An agent can aggregate them, identify interesting regions, generate the next inputs, and continue the experiment. While rating remains the largest component of tₛ and the experiments have comparable value:

hypotheses tested per session ∝ rating throughput

The compiler gives an agent fast structural feedback while it writes a rater. This system gives it fast empirical feedback once the rater runs. Both increase how much useful work fits inside one agent loop.

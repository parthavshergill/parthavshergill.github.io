Turning a type into a test generator

In Designing a compiler for an agent-written DSL, I described an insurance rater as a total function over its valid inputs. Every valid input should produce either a premium or an explicit business rejection.

The phrase “valid input” hides quite a lot of work. A homeowners rater might require the roof year to be no earlier than the construction year, allow different deductibles for different states and coverages, and require references between locations, buildings, and policies to form a valid entity graph. These rules overlap: changing one field can make several other choices invalid.

An agent can construct examples by reading the program and repeatedly fixing validation errors. This works, but it spends tokens rediscovering a contract the program already contains. It also makes large or deliberately varied input sets annoying to produce.

RSL supports a fixed set of input types and requires every input domain to be explicit. Start with every value that has the right shape. A record chooses one value for each field. A Boolean chooses between two values, an enum such as Occupancy chooses one member of a fixed set, and an optional alarm chooses between no alarm and an Alarm. Numbers and dates have declared bounds. Entity declarations determine how policies, buildings, locations, drivers, and vehicles may refer to one another.

These constructions give us the set Fields. Records combine values, while Booleans, enums, and optionals choose among alternatives (in type theory, these are product and sum types). The program’s relationships and requires rules select the valid subset:

ValidInputs = { x ∈ Fields | relationships(x) ∧ requires(x) }

A type restricted by a predicate is called a refinement type. Because RSL declares both the shape and the predicates, generating an input means finding any value in this set:

find x ∈ ValidInputs

Finding a value of a given type is called type inhabitation. Here the compiler can do it directly from the program instead of asking an agent to reason through the contract.

This is separate from rating eligibility. A contract-valid input may still produce an explicit rejection such as “outside underwriting appetite.” Input generation only establishes that the rater has received a well-formed risk within its declared domain.

What properties do we want?

  • Valid by construction. Every returned input satisfies field domains, entity relationships, and every requires rule.
  • Useful coverage. Small batches cover Boolean and enum members, numeric and date boundaries, and literals mentioned by constraints before filling in interior values.
  • Distinct and deterministic results. A generator version, contract hash, seed, and row index determine the same input.
  • Bounded work. A difficult contract produces a resource error instead of consuming an unknown amount of time or memory.
  • Specific invalid inputs. A negative witness violates one named rule, so the resulting diagnostic has a clear cause.

The simplest generator chooses one value from each field and checks the result:

repeat:
    choose a value for every field
    build the entity graph
    return the input if every constraint passes

If valid inputs occupy a fraction p of the structural input space, the expected work is:

expected attempts per result = 1 / p

That is fine for loose constraints and unpleasant for sparse ones. A rule requiring a number to belong to a short fixed list can make almost every random number useless. Several overlapping choices can make a repair routine explore the product of their branches.

We can instead turn each finite choice into bits. A Boolean needs one bit. An enum with k members needs ceil(log2 k) bits, plus a bound that rules out unused bit patterns. Numbers and dates use fixed-width integers constrained to their declared ranges.

The compiler can then lower a rule to Boolean choices joined by or, and require all of those rules at once with and. A small fragment might look like:

(owner_occupied ∨ landlord_endorsement) ∧ (¬coastal ∨ wind_deductible_selected)

More generally, the resulting formula has the shape:

(choice ∨ choice ∨ ...) ∧ (choice ∨ choice ∨ ...) ∧ ...

This is called conjunctive normal form, or CNF. The compiler lowers supported RSL expressions and their finite encodings into this form exactly.

To find an input, choose an unassigned bit. If that choice leaves a rule with only one way to be true, make the forced choice. If it makes a rule impossible, undo decisions until another branch is available:

choose an unassigned variable
propagate forced assignments
if a rule is impossible, backtrack
if every rule is satisfied, return the assignment
otherwise continue

The forced step is called unit propagation. A modern solver also records each contradiction as a new rule and jumps back to the decision that caused it, avoiding the same dead end later (conflict-driven clause learning, or CDCL; see: An Extensible SAT-solver).

We use RustSAT to build the encodings and its MiniSat adapter to solve them. Independent groups of constraints can be solved as separate components, while a large single-field membership rule stays as a direct native set rather than becoming thousands of Boolean clauses. SAT remains exponential in the worst case, so construction, clauses, variables, memory, and solver time all have explicit limits.

One satisfying assignment is only the beginning of a useful sampler. We first choose something worth covering, such as a particular enum member or numeric boundary, and ask the solver for an input that contains it:

next input = solve(contract ∧ target ∧ unseen)

After each result, we add one rule saying that exact combination cannot recur (a blocking clause). The same solver session can then produce another input without rebuilding the contract. Once the useful boundaries and alternatives are exhausted, a seeded stream supplies interior targets for the rest of the batch.

The solver is a model finder, while the compiler remains the authority on RSL semantics. We materialize each assignment as an input and pass it through the Core input judge before returning it. A solver bug, unsupported encoding, or disagreement therefore fails generation instead of admitting an invalid row.

Valid witnesses also give us good starting points for negative ones. For each declared rule, the compiler mutates a valid base toward a violation and keeps the result only when the Core judge reports exactly that rule and no others:

valid witness: every declared rule passes negative witness: one named rule fails; every other rule passes

These cases are more useful than arbitrary malformed inputs. They let us test the boundary of one field, relationship, or constraint without accidentally testing three unrelated failures at the same time.

This is close to property-based testing, except that RSL already contains the generator’s domain and predicates. Work such as Beginner’s Luck treats constrained test generation in much the same way: construct values from predicates instead of maintaining a separate handwritten generator.

For an agent, rslc inputs sample turns the program it just wrote into a deterministic batch of valid risks. It can run those risks through the rater and look for premiums that vanish, blow up, or cluster at suspicious values. It can pin nearby values around a boundary to find cliffs, reversed monotonicity, or inputs that unexpectedly have no effect.

The same batch also makes a useful regression fixture. An agent can rate it before and after an edit, isolate the rows whose results changed, or send it through two runtime backends and compare their outputs. It can measure which valid regions produce business rejections, then generate more inputs around an unexpected pocket of appetite. Through the compiler API, isolated invalid witnesses let it check that each broken rule produces the intended diagnostic without tripping unrelated validation first.

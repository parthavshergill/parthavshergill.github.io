Turning a type into a test generator

One useful thing falls out of making a program’s input contract explicit: the compiler can generate inputs from it.

In Designing a compiler for an agent-written DSL, I described an insurance rater as a total function over its valid inputs. An agent writing one needs valid inputs to check what the program actually does. It can assemble JSON and repeatedly fix validation errors, but that spends tokens rediscovering a contract the program already contains.

Consider a small homeowners input:

Types = {
  Year = Num { precision: int, range: [1900, 2026] },
  Territory = Num { precision: int, range: [1, 999] }
}

Entities = {
  Home = {
    inputs {
      construction_year: Year,
      roof_year: Year,
      territory: Territory,
      coastal: Bool,
      wind_deductible: Bool
    }
    requires exact {
      self.roof_year >= self.construction_year,
      self.territory in { 4, 11, 42 },
      not self.coastal or self.wind_deductible
    }
  }
}

The field types describe all structurally possible homes. The three rules carve out the values the rater accepts:

ValidHomes = { x ∈ Homes | constraints(x) }

A type narrowed by a predicate is called a refinement type. Generating an input means finding a value in it, which is called type inhabitation.

This is separate from underwriting appetite. A valid input can still produce an explicit business rejection. Here, validity only means the program received a well-formed risk from its declared domain.

Guess and check

The first implementation writes itself:

repeat:
    choose a value for every field
    return it if every constraint passes

If valid inputs occupy a fraction p of the structural space:

expected guesses per input = 1 / p

For the example above, roughly half of the year pairs have a roof at least as new as the house, three quarters of the Boolean pairs satisfy the coastal rule, and three of 999 territory codes are allowed.

p ≈ 1/2 × 3/4 × 3/999 ≈ 1/900

That is already a lot of wasted work for five fields. Real input contracts contain more fields and overlapping rules, so repairing one choice can invalidate another.

Compile the choices

We can avoid guessing by turning the finite choices into bits. A Boolean needs one bit. An enum with k members needs ceil(log₂ k) bits, plus a bound excluding unused patterns. Numbers and dates use fixed-width integers within their declared ranges.

The coastal rule is already a Boolean clause:

¬coastal ∨ wind_deductible

The compiler lowers the other supported constraints into the same shape, joins the clauses with and, and asks a SAT solver for values that make them all true (this shape is conjunctive normal form, or CNF). The solver assigns bits, propagates choices that have become forced, and remembers contradictions instead of exploring them again.

We use RustSAT with MiniSat. A constraint involving only membership in a fixed set remains an ordinary set; we use SAT where choices interact. Solver variables, clauses, memory, and time are all bounded because SAT still has exponential worst cases.

From one input to a useful sample

A solver will happily return the same easy corner of the domain every time. We instead ask it to cover a particular Boolean value, enum member, numeric boundary, or constraint literal. After each result, we add a clause excluding that exact input and solve again:

next input = solve(contract ∧ coverage target ∧ unseen)

Once those targets are exhausted, a seed determines the remaining interior values. The command returns the requested number of distinct inputs or explains why the domain does not contain enough of them.

The solver only proposes candidates. The compiler’s Core input judge checks every result before returning it, so there is still one authority on what RSL accepts.

Valid inputs also make useful starting points for invalid ones. The compiler changes one toward a named rule and keeps it only when the judge reports exactly that violation:

violations(input) = { target rule }

For an agent, rslc inputs sample turns the program it just wrote into a batch it can use immediately. It can look for premiums that vanish or blow up, probe boundaries for cliffs or reversed monotonicity, compare results before and after an edit, and find valid regions that unexpectedly produce business rejections. This is constrained property-based generation with the program itself supplying the generator (see: Beginner’s Luck).

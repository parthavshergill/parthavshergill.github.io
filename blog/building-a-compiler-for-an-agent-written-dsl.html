Designing a compiler for an agent-written DSL

I recently got to build a compiler for a domain-specific language at work. At Effective, one product we offer is the ability to design, host, and reverse-engineer pricing algorithms from public rate filings. I wrote a little about our initial experiments with this idea here.

The gist of it is that rating algorithms, or raters, compute an insurance premium from a large number of factors and input values. In practice, a rater is a giant deterministic program made from table lookups, arithmetic, branches, and aggregation over objects. These programs are valuable because they encode how an insurance carrier prices risk in a market.

A deployed rater should behave like a total function over its declared input type: every valid input should produce either a rating result or an explicit rejection. This gives us some useful constraints for a compiled, executable DSL (Rating Specification Language or RSL) that seems easier for agents to reason about than a more flexible language like Python or TypeScript, probably because agents do very well at writing code until a compiler stops yelling at them.

Eventually, either models will get good enough to one-shot these programs in any programming language from a universe of PDF and Excel data and we can throw out RSL and its compiler, or RSL will become valuable enough for us to train a model that is particularly good at writing it.

What properties do we want?

At a high level, we want to make it hard to represent a rater that is ambiguous, incomplete, or impossible to inspect.

  • One source of truth for semantics and backend parity. The native evaluator, Python export, Excel export, and JSON representation should all be projections of the same typed program, rather than separate implementations of what RSL means.
  • The standard properties of a total function. For any valid input, the rater should produce either a rating result or an explicit rejection, and the same program, tables, and inputs should always produce the same result.
  • Total lookups. If a program reads from an ordinary rating table, every possible runtime key should resolve unambiguously to a value under that table’s matching rules.
  • Static errors where possible. Missing references, incompatible types, malformed tables, and other structural problems should fail at compile time rather than turn into strange premiums at runtime.
  • Introspection. The compiler should be able to answer questions like: what does this value depend on, which source filing did this calculation come from, what inputs can reach this branch, and what table does this lookup use?

Why write a compiler?

We needed a few things from a product standpoint:

  • We offer the ability to export raters as Python or Excel, and need JSON to power some UIs.
  • We need to introspect on the program so the agent has a richer set of debugging tools than an out-of-the-box compiler provides.
  • A constrained DSL reduces the review surface. More flexible languages gave agents too many escape hatches for setting default values, implementing standard operations in inefficient ways, and wasting tokens on irrelevant boilerplate.
  • A compiled DSL lets us enforce things that would be annoying for humans to maintain manually, such as citations to source documents, explicit rating outcomes, and proofs that ordinary table lookups are total over their declared domains.

The version from the earlier blog post was a Python approximation of a compiler, which became quite limited as we encountered more complex production rating structures. Maintaining three implementations of RSL semantics in Python (the native evaluator, Python export, and Excel export) became a long loop of iterative fixes to keep them in sync as we added features to the language. More generally, agents were causing the codebase to tend toward a mess of stringly typed objects that undermined the guarantees we wanted the compiler to provide.

We wanted the RSL compiler to be easy for agents to maintain and extend, so I rewrote it in Rust with the help of Codex. Writing a compiler with agents was its own experiment, with its own creative verification mechanisms, and probably deserves a post of its own.

Why Rust?
  • Compilation is a series of typed transformations. When implemented efficiently, each transformation establishes facts that the next stage can rely on. When we add an IR node for a new language feature or syntax, Rust’s algebraic data types and exhaustive pattern matching help ensure that every backend handles it or the project will not compile.
  • Rust makes data ownership choices such as moving, borrowing, and cloning explicit and compiler-checked. Most compilers use arenas to store program data efficiently. An arena owns each node once, while compiler stages pass around references or small IDs instead of copying the underlying data. We apply the same principle to large RSL lookup tables with the help of Rust’s Arc: load each table snapshot into memory once, check totality against it, and reuse that exact snapshot across compiler stages.
  • We also want to take advantage of Rust’s ecosystem. PyO3 gives us Python bindings, while rust_xlsxwriter writes XLSX files directly without the memory overhead we encountered with openpyxl. This let us move more logic into a compiler-checked core instead of duplicating it across backends. Also, ts-rs gives us a path toward TypeScript bindings, and libraries such as DataFusion may become useful as our table analysis grows more demanding.
  • The Rust compiler itself is a useful reference for how to structure a compiler. Since I was learning about both compiler design and Rust as I went, that was helpful.

Ultimately, RSL looks like a small, statically typed spreadsheet language. It has entities with inputs and computed values, pure expressions, explicit relationships, and tables as first-class declarations. Here is a toy example:

spec {
  carrier: "Example Mutual",
  state: CA,
  product: "Homeowners",
  effective_date: 2026-08-30,
}

Sources = {
  manual: Source = {
    path: "rate-manual.pdf",
    title: "Homeowners Rate Manual"
  }
}

Types = {
  Factor = Num { precision: factor },
  Premium = Num { precision: cents }
}

Tables = {
  AlarmFactors [cite: manual:p12] :
    (Policy.has_alarm) -> { factor: Factor }
    match: specific
    columns: {
      has_alarm: "has_alarm" [type: Bool],
      factor: "factor" [type: Factor]
    }
}

Entities = {
  Policy = {
    inputs {
      base_premium: Premium,
      has_alarm: Bool
    }
    requires {
      self.base_premium >= 500,
      self.base_premium <= 2000
    }
    step rating {
      alarm_factor: Factor =
        lookup!(AlarmFactors, self.has_alarm).factor,
      written_premium: Premium =
        self.base_premium * self.alarm_factor
    }
  }
}

RatingOutcomes = {
  written_premium: Policy.written_premium
}

true,0.95
false,1.00

Two of the more unusual features of rslc, the compiler’s CLI, are:

  • rslc check loads the tables in a complete rater bundle and proves that every valid runtime key resolves unambiguously to a value under the table’s matching rules. This needs to be fast because agents run it as they write RSL files, allowing us to catch possible table-extraction errors early.
  • rslc inputs sample constructs valid inputs from the domain described by the program’s types, ranges, entity relationships, and constraints. The same input-contract machinery can generate targeted invalid inputs through the compiler API. Both paths need to be fast enough to generate large batches that we can run through the rater to sanity-check premium ranges and rejection messages.

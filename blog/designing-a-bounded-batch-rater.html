The perks of having a wall-time formula

At Effective, we build and host insurance rating algorithms. A rater takes a description of a risk and returns a premium or an explicit rejection. Calling one is an ordinary API request, while calling one over enough carefully chosen inputs gives us a way to study how an insurance carrier prices a market.

The deployed raters discussed here are generated Python programs, although the architecture only assumes that loading a rater is expensive enough to amortize across many inputs; the same design also applies to a future native RSL runtime.

AI slop is a bit like MSG for blog posts: a small amount makes them look more tasteful. I had Codex draw the diagrams and typeset the formulas in this one.

Let N be the number of inputs and R the number of raters. We can set N = 100,000 and R = 1 to look for discontinuities, surprising interactions, and changes in eligibility within one carrier. We can also set N = 10,000 and R = 10 to compare appetite and premiums across carriers. Both experiments produce NR = 100,000 ratings. They are most useful when they finish quickly enough for an analyst or agent to inspect the result, form another hypothesis, and run the next one in the same session.

The naive execution path would have taken about 31 minutes to rate 100,000 inputs against one rater.

A batch can be arbitrarily large, while a process has finite memory. We represent the batch as a variable number of fixed-size, immutable partitions and give each executor a bounded amount of work. Let P be the maximum number of rows in a partition.

partitions = ⌈N / P⌉ tasks = R⌈N / P⌉

This is similar to Static Allocation, Constant Work: decide what the system promises to handle, make operation at that limit predictable, and reject excess work before the machine discovers the limit through an out-of-memory kill.

total work = Θ(NR) work per task = O(P) = O(1), for fixed P

What properties do we want?

At a high level, we want increasing the size of a batch to create more bounded work instead of larger processes or more complicated execution paths.

  • Bounded memory. An API process, workflow, or worker should only need to hold one bounded page or partition of data.
  • Deterministic identity. Every partition, rater invocation, and output should have an identity derived from the run so a retry converges on the same result.
  • Durable partial progress. Once a partition result is committed, a process crash should not require it to be computed again.
  • Ordered results. Parallel execution should produce the same observable order as a simple sequential map over inputs and raters.
  • Explicit concurrency. The number of large rater processes should follow from the number of physical workers, without multiplication through nested application-level pools.
  • A small control plane. Workflow state should contain references and completion state while object storage contains the input and output data.
Why Temporal?
  • A batch run is a long-lived coordination problem. Temporal records which partitions exist, which activities completed, and which need to be retried when a worker disappears.
  • Workflows give us a deterministic place to express admission, cancellation, ordering, and the final commit. Activities contain the fallible operations: reading artifacts, starting runtime processes, evaluating raters, and writing results.
  • Task queues provide a durable buffer between logical concurrency and physical capacity. A workflow can describe all available work while a bounded worker fleet decides how much runs simultaneously.
  • Activity retries compose well with immutable artifacts and deterministic IDs. Repeating an activity either creates its expected result or observes that the result already exists.
  • Temporal history remains small when workflows carry typed artifact references instead of input rows and rating results. The data plane can grow independently in object storage.

1. Amortize fixed overhead inside a bounded unit

For rater r, let eᵣ be the average evaluation time for one input and Fᵣ the fixed cost of acquiring a worker, loading the rater, crossing a process boundary, validating a request, and committing its result.

one row per task ≈ N(Fᵣ + eᵣ) P rows per task ≈ ⌈N / P⌉Fᵣ + Neᵣ time per partition ≈ Fᵣ + eᵣP

A bulk operation sends an ordered partition through an already loaded rater process.

|request| ≤ P |outcomes| = |request|

Mapping failures and rating failures remain attached to their input positions, so batching does not weaken the row-level contract.

The same boundary works for persistence. A partition produces a bounded collection of deterministic execution records, which can be inserted with one atomic database operation.

database round trips: N → ⌈N / P⌉

Bulk execution and atomic persistence reduce the projected 100,000-input path from about 31 minutes to 4 minutes and 59 seconds.

2. Keep O(N) data outside O(1)-memory executors

Passing a file identifier to an API only helps if the API leaves the file where it is. Downloading the complete artifact before starting a workflow moves the memory limit from the HTTP request to the API process.

The run API accepts an immutable input manifest. Each partition reference includes its artifact identity, content digest, storage generation, and row range. The workflow passes these references to activities, and each activity reads only the partition it owns.

Outputs use the same representation. A completed (partition, rater) task writes one immutable rated artifact, and the final output is a compact ordered manifest of those artifacts. Individual rating executions remain useful for search and UI history, but a separate durable workflow can populate that index after the output manifest commits.

artifact storage = O(NR) control-plane state = O(R⌈N / P⌉) executor memory = O(P) = O(1), for fixed P

Streaming input preparation and moving execution indexing after completion reduce the measured 100,000-input execution time to 3 minutes and 8 seconds.

3. Make computation, persistence, and retry the same unit

The natural unit of work for a batch containing several raters is the pair (partition, rater). It maps one partition into one rater’s input schema, evaluates the mapped rows with one loaded rater process, and writes one rated artifact.

The mapper is small and short-lived. It exits before the rater is loaded, which keeps arbitrary mapper code isolated without making two large processes compete for the same memory. The rater process then owns the bulk evaluation until the bounded partition finishes.

This activity is also the persistence and retry boundary. Its deterministic artifact ID lets a retry reuse a result that was committed before an acknowledgement was lost.

maximum recomputation after failure ≤ P ratings

The output manifest gathers independently computed artifacts in input and rater order. No worker needs to download all of them and construct another copy of the output. Partition-native execution reduces the measured time for 100,000 ratings to 1 minute and 58 seconds.

4. Scale by adding fixed-capacity workers

Once an activity has a fixed resource envelope, physical concurrency becomes a deployment choice. Each partition worker admits one activity and loads one rater process. Additional work waits in Temporal, where it consumes queue capacity instead of process memory.

The workflow controls how many durable tasks may be outstanding. Kubernetes controls how many workers may execute them. These are separate limits because workflow history and machine capacity have different constraints.

Task-queue depth provides the demand signal for autoscaling. Partition workflows and their rating activities share the dedicated partition queue, which also lets Temporal hand an activity directly to the worker that completed the preceding workflow task. KEDA observes both workflow and activity backlog and adds workers until the amount of queued work approaches the configured target.

Let W be the number of workers. Scheduling, queue handoffs, autoscaling delay, and unequal task durations keep some fraction of that capacity idle, so let U ∈ (0, 1] be worker utilization.

wall time ≈ N / UW · Σᵣ(eᵣ + Fᵣ/P) executor memory = O(P) fleet memory = O(PW)

With eager partition dispatch and activity-aware scaling, the 100,000-input run completed in 1 minute and 51 seconds.

Where is the headroom?

There is still a lot of headroom, and the wall-time estimate gives us a useful order in which to look for it:

wall time ≈ N / UW · Σᵣ(eᵣ + Fᵣ/P) 1% ↑ W or U → ≈ 1% ↓ wall time 1% ↓ eᵣ → [eᵣ / Σᵣ(eᵣ + Fᵣ/P)] × 1% ↓ wall time 1% ↓ Fᵣ → [(Fᵣ/P) / Σᵣ(eᵣ + Fᵣ/P)] × 1% ↓ wall time ∂ wall time / ∂P ∝ -1/P²

For the common case in which evaluating a rater costs more than starting it, this suggests the following ranking:

  1. U ↑, then W ↑. Both have unit elasticity. Recovering idle worker capacity through eager dispatch, short queue handoffs, and balanced tasks comes first; adding workers provides the same proportional effect once the existing fleet stays busy. Both stop scaling when the queue or another shared resource cannot supply enough work.
  2. eᵣ ↓. Optimize the raters with the largest eᵣ terms. A native RSL evaluator, better table indexes, and optimization of common expression paths reduce work paid once for every input. Raters vary widely here because their programs and tables vary widely.
  3. Fᵣ ↓. Optimize the raters with the largest Fᵣ/P terms by keeping prepared raters and parsed tables warm, reducing serialization, and making artifact commits cheaper. A workload dominated by loading very large bundles can move this ahead of evaluator work.
  4. P ↑. Larger partitions reduce only Fᵣ/P, with a marginal return that decays as 1/P², while executor memory grows as O(P). Increasing P is useful until the partition approaches the worker’s configured memory limit or Fᵣ/P ≪ eᵣ. Smaller partitions may still win when they raise U by balancing raters with different runtimes.

Measurements of evaluation time, fixed task time, memory per row, and utilization tell us whether this default ranking applies. The formula turns those measurements into an expected wall-time change before we implement the optimization.

What does this let us learn?

A fast batch rater turns a deployed pricing algorithm into something we can probe experimentally. RSL already declares the valid input domain of a rater, so the compiler can generate large sets of valid risks as well as targeted inputs near type, table, and eligibility boundaries.

One experiment might start with 20,000 valid base risks and create four controlled variations of each. Changing a deductible, building age, limit, or other rating input one at a time gives us 100,000 points on the pricing surface. We can measure marginal premium effects, find discontinuities at rating bands, check expected monotonic relationships, and locate interactions where the same change behaves differently across segments.

Another experiment can send 10,000 representative risks through ten carrier raters. The resulting 100,000 premiums describe where carriers quote, where their appetites overlap, which carrier is cheapest for each segment, and where small changes in a risk reverse their relative position.

At 31 minutes, each question becomes a background job and encourages us to choose a few representative examples. At two minutes, an analyst or agent can inspect the result and ask a better follow-up while the context is still fresh. Bounded execution makes the infrastructure predictable, and predictable infrastructure makes the rating algorithms easier to understand.
